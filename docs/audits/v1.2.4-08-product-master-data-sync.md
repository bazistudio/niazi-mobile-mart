## 2. Product Data Model

Based on the inspection of `001_initial_schema.sql` and `src-tauri/src/repositories/product_repository.rs`:
* **Scope**: Products are **organization-wide master data**. The `products` table does not contain a `branch_id` column; product domain catalog entities belong to the organization.
* **Stock Isolation**: Physical inventory quantities are tracked separately per branch in the `stock` table (`product_id`, `branch_id`, `quantity`).
* **Deactivation Guardrail**: "Remove" in product CRUD strictly means soft-deletion/deactivation (`is_active = false` / `is_active = 0`). Physical row deletion is prohibited.

---

## 3. Event Types

Defined event types:
1. `PRODUCT_CREATED`: Enqueued on desktop product creation. Payload contains full `Product` domain entity.
2. `PRODUCT_UPDATED`: Enqueued on desktop product update. Payload contains updated `Product` domain entity.
3. `PRODUCT_DEACTIVATED`: Enqueued on desktop product deactivation. Payload contains `{ "id": "<product_id>" }`.

## 4. Local Outbox Flow

```text
Product Service (PC-A)
  ↓
BEGIN SQLite Transaction
  ↓
Product Table Insert/Update/Deactivate
  ↓ (optional opening stock insert/movement if initial_quantity > 0)
Enqueue event (PRODUCT_CREATED / PRODUCT_UPDATED / PRODUCT_DEACTIVATED) into offline_sync_queue
  ↓
COMMIT SQLite Transaction
```

Atomicity: SQLite product table write and outbox enqueue occur inside a single `with_transaction` block. If either fails, both roll back.

## 5. Central Flow

```text
SyncWorker (PC-A)
  ↓
POST /api/v1/sync/push
  ↓
Axum sync_push_handler
  ↓
JWT Authentication & Org/Branch Scope Validation
  ↓
BEGIN PostgreSQL Transaction
  ↓
Idempotency Check (PostgresSyncAuditRepository::find_existing_event_id_tx)
  ↓
Central Product Projection:
  - PRODUCT_CREATED → PostgresProductRepository::create_product_tx
  - PRODUCT_UPDATED → PostgresProductRepository::update_product_tx
  - PRODUCT_DEACTIVATED → PostgresProductRepository::deactivate_product_tx
  ↓
Central Change Log Append:
  - PostgresChangeLogRepository::append_change_log_tx
  ↓
Sync Audit Record:
  - PostgresSyncAuditRepository::record_audit_tx
  ↓
COMMIT PostgreSQL Transaction
  ↓
HTTP 200 OK SYNCED
```

Transaction Invariant: Central projection, change log entry, and sync audit record commit in a single PostgreSQL transaction owned by `sync_push_handler`.

## 7. Idempotency

* `client_event_id` is passed with every push event and is checked against `sync_audit` in the central PostgreSQL transaction.
* If a push with the same `client_event_id` is replayed, `sync_push_handler` detects the existing audit record, rolls back the transaction, and returns the existing `"status": "SYNCED"` response without re-projecting or appending duplicate `change_log` entries.
* Product domain identity `product.id` (UUID) remains separate from `client_event_id`.

---

## 8. Replay Safety

* `PRODUCT_CREATED`: Downstream `ChangeApplier` checks `SELECT 1 FROM products WHERE id = ?1`. If the product already exists locally, insertion is safely skipped.
* `PRODUCT_UPDATED`: Uses `ON CONFLICT (id) DO UPDATE...` to update master data fields deterministically.
* `PRODUCT_DEACTIVATED`: Sets `is_active = 0` deterministically.
* Product master-data sync does NOT touch inventory balances, cash balances, or sales/purchase transactional ledgers.
